# 微调的定位:它属于训练,但可以平行地学

目标:回答四个问题——微调在 LLM 生命周期里处于什么位置?微调家族有哪些
成员、各自解决什么?微调能改变什么、不能改变什么?面对一个需求,
prompt / RAG / 微调怎么选?

## 1. LLM 的生命周期:预训练 → 后训练 → 推理

| 阶段 | 输入 | 目标 | 数据量级 | 算力量级 | 产出 |
|---|---|---|---|---|---|
| 预训练 | 随机初始化权重 | 学会语言与世界知识(next-token prediction) | TB 级无标注文本 | 千卡 × 数月 | base model |
| 后训练 | base model | 对齐人类意图:会对话、守规矩、有偏好 | 几千~几百万条标注/偏好数据 | 单卡~数百卡 × 小时~天 | instruct/chat model |
| 推理 | 训练好的权重 | 权重冻结,只前向,服务请求 | — | 单卡~集群 | token 流 |

**微调(fine-tuning)是后训练的主体**。机制上它与预训练完全同构:
前向算 loss → 反向传播 → 优化器更新权重。两者的差别只是配置:

| | 预训练 | 微调 |
|---|---|---|
| 起点 | 随机初始化 | 预训练权重 |
| 学习率 | ~1e-4,精心调 warmup 与 schedule | ~1e-5(全量)/ ~1e-4(LoRA),小一至两个量级 |
| 步数 | 几十万 step | 几百~几千 step |
| 灾难性遗忘风险 | 无(没有可忘的) | **有,是主要风险** |
| 显存账 | 权重+梯度+优化器+激活 | 同一套账,只是规模小 |

所以"微调 vs 推理"的界限是**本质的**(是否更新权重、是否需要反向传播),
而"微调 vs 预训练"的界限是**程度的**(同一机制、不同规模)。

为什么又可以当作平行领域来学:预训练的核心难题——千卡并行的通信、
数据配比、loss spike 与训练稳定性——在微调里几乎不出现;微调有自己的
独立知识体系(PEFT 数学、对齐算法、数据工程),预训练专家也未必熟。
本系列默认读者读过 `docs/inference/`(或至少其 01/02/04 篇),
推理知识是本系列的地基之一。

## 2. 微调家族谱系

两个正交的分类轴:

**按"更新多少权重"分**:

```
全量微调(full fine-tuning)
  └─ 更新所有权重;显存账 = 训练账(02 篇),7B 就要 ~112 GB
PEFT(参数高效微调)
  ├─ LoRA / QLoRA   :冻结主干,只训低秩旁路(04/05 篇)——本系列主线
  ├─ Adapter        :在 block 内串行插入小 bottleneck 层
  └─ Prompt/Prefix tuning:只学输入侧的一小段"软提示"
```

**按"用什么信号训"分**:

- **SFT(监督微调)**:给定 (指令, 标准回答) 对,模仿回答。教格式、教
  任务模式、教口吻。一切微调的第一步。
- **偏好对齐(preference alignment)**:给定 (指令, 好回答, 差回答),
  学"哪个更好"。RLHF(PPO)、DPO、GRPO/RLVR 属于此类(06 篇)。
  解决 SFT 学不到的东西:拒绝什么、两个合格回答里哪个更好。
- **蒸馏(distillation)**:用强模型的输出当训练数据,是数据来源手段,
  通常套在 SFT 或偏好对齐的壳里。

实践中一次完整的后训练 = SFT → 偏好对齐(可选多轮),各自可以用全量或
PEFT 的方式执行。

## 3. 微调能改变什么、不能改变什么

经验法则(**表面对齐假说**,LIMA 论文,07 篇展开):模型的知识与能力
在预训练时已成型,微调主要是教它**用哪种方式展示已有能力**,而不是
注入新能力。

**适合微调做的事**:

- 输出格式与结构:固定 JSON schema、"分析:...结论:..."的答题模板;
- 风格与口吻:客服语气、领域黑话、角色人设;
- 任务模式:特定分类标签体系、工具调用的触发时机;
- 偏好与边界:哪些该拒绝、两个回答里更喜欢哪种(偏好对齐)。

**不适合微调做的事**:

- 注入大体量新知识(如"学完我司全部内部文档"):数据少了记不住,
  数据多了过拟合+遗忘,还会学会"一本正经地编"——用 RAG;
- 追赶时效性知识:训练完即过时——用 RAG;
- 根本性提升推理能力:那是预训练/RLVR 大规模投入的战场,小作坊微调
  提升有限。

判据一句话:**要改"怎么说"用微调,要补"知道什么"用 RAG,
只是个别场景的规则用 prompt。**

## 4. prompt / RAG / 微调的选型

| 需求 | 首选 | 理由 |
|---|---|---|
| 单次/低频任务,规则一句话说清 | prompt | 零成本,随时改 |
| 需要私有/时效知识 | RAG | 知识外置,可更新、可溯源 |
| 需要固定输出格式/风格,或 prompt 太长太贵 | 微调 | 把长 prompt "烧进"权重,推理时零开销 |
| 需要模型拒绝某些行为、表达偏好 | 微调(偏好对齐) | prompt 约束不可靠 |
| 高频调用小模型替代大模型 | 微调(蒸馏) | 成本账:一次训练换永久推理降价 |

三者不互斥:生产系统常见组合是"微调定格式与行为 + RAG 供知识 +
prompt 做临场指令"。

成本视角补充:微调有一次性训练成本 + 维护成本(基座模型升级要重训),
所以**先用 prompt 顶到顶不住,再 RAG,最后才微调**是稳妥顺序。

## 5. 与推理的关系:上下游,外加两个交叉点

微调产出新权重,推理消费权重——标准的上下游。两个具体交叉点:

1. **QLoRA 复用推理量化的知识**:QLoRA 的 NF4、双重量化与推理 4bit
   (GGUF Q4 等)是同一家族的技巧,差别只在"训练时计算要回 bf16"
   (05 篇详述);
2. **LoRA 的两种部署方式**:merge 回主干得到一个普通模型,走正常推理
   流程(本系列 08 篇的做法);或不 merge,由推理引擎动态加载 adapter
   (vLLM 支持多 LoRA 热切换,一个基座服务多个租户/任务)。

反向的衔接:微调出来的模型最终要部署,部署时的显存/速度账、量化、
serving 方案全部回到 `docs/inference/` 的框架里——两个系列在 08 篇
合流。
