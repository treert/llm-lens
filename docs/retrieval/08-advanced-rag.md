# 进阶形态:Agentic RAG、GraphRAG 与记忆

vanilla RAG 的隐含假设是"单次检索 + 一次生成就能解决问题"。
本篇讨论这个假设破产的三种场景,以及对应的三种进阶形态:
检索变成 agent 的工具(Agentic RAG)、答案不在任何局部 chunk(GraphRAG)、
知识库变成会生长的(长期记忆)。

## 1. 固定流水线的天花板

单次 RAG 在这些场景失效:

- **多跳**:答案分散在多个文档,一次检索覆盖不了
  ([06-query-and-retrieval-strategy.md](06-query-and-retrieval-strategy.md) §4);
- **首次检索失败**:问法不对需要换个角度再查,流水线没有"再来一次"的机制;
- **全局性问题**:"这个语料库主要讲什么"——答案不存在于任何局部片段。

共同的主题:检索从"前置步骤"变成"**可重复、可决策的动作**"。

## 2. Agentic RAG:检索作为 agent 的工具

### 2.1 结构

把检索封装成 tool,嵌入 agent 循环:

```
思考(我需要什么信息?) → 调检索工具(查什么?) → 观察结果
  → 不够:改写/分解后再查  →  够了:生成答案
```

与 ReAct/工具调用范式完全同构——RAG 退化为 agent 的若干工具之一
(与计算器、代码执行器并列)。这正是当前 agent 系统获取知识的主流形态。

### 2.2 自我反思

self-RAG 的思路:给生成过程加三类反思信号——
这步需要检索吗?检索结果相关吗?我的答案被检索内容支持吗?
工程上不必照搬反思 token 的训练,用规则就能实现 80%:
"检索最高分低于阈值 → 改写重查一次"是最常见的一条。

### 2.3 成本账

token 消耗 ≈ 步数 × 单步消耗,延迟随步数线性叠加。
实用架构是**按问题复杂度路由**:

- 简单事实问答 → 单次 RAG(快、便宜);
- 复杂分析、多跳 → agentic 循环(慢、贵,但能做下来)。

让 router(小模型或规则)先分诊,比所有问题都上 agent 省一个数量级。

## 3. GraphRAG:为全局性问题建图

### 3.1 问题

"这份研报库对新能源的整体态度是什么""A 公司与 B 公司的关系网"——
答案不在任何 chunk 里,而在**跨文档的聚合结构**里。
向量检索的粒度(局部片段)与问题的粒度(全局)根本错配。

### 3.2 管线

```
chunk → LLM 抽取(实体, 关系, 声明) → 知识图谱
      → 社区检测(Leiden 算法)分层聚类
      → 自底向上生成社区摘要(小社区摘要 → 大社区摘要)
```

查询时分流:全局问题走社区摘要的 map-reduce(各社区摘要先答再汇总);
局部问题仍走向量检索的老路。图谱同时提供了实体间的显式关系路径,
多跳问题也能沿边游走。

### 3.3 成本与适用

离线抽取的 LLM 调用量正比于 chunk 数——建库成本是 vanilla RAG 的几十倍。
适用:**语料相对稳定 + 需要全局理解**(研报库、法律卷宗、企业知识库);
语料高频更新或问题都是局部事实时,这笔钱不值得花。

## 4. 长期记忆:会写的 RAG

agent 的长期记忆系统在检索技术上完全复用 RAG(向量库 + 元数据),
本质区别在于**写路径**:

- **写入**:对话结束后,什么值得存?(LLM 判断 + 去重)
- **更新**:新记忆与旧记忆冲突怎么办?(覆盖、版本化、时间衰减)
- **遗忘**:低价值记忆的淘汰策略。

知识库是共享的、静态的;记忆是 per-user 的、生长的——
建模与评估都要围绕这个区别展开。

## 5. 形态对比与演进路径

| 形态 | 解决的问题 | 延迟 | 建库成本 | 工程复杂度 |
|---|---|---|---|---|
| vanilla RAG | 局部事实问答 | 低 | 低 | 低 |
| + 混合检索/rerank | 召回精度 | 低-中 | 低 | 中 |
| Agentic | 多跳、需反思的复杂问题 | 高 | 低 | 高 |
| GraphRAG | 全局性、关系性问题 | 中 | **高** | 高 |

建议的演进路径:**先把 vanilla + 混合检索 + rerank 做扎实**
(覆盖约 80% 场景),然后由具体的失败 case 驱动升级——
为问题升级,不为技术升级。
