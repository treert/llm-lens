# RAG(检索增强生成)

RAG(Retrieval-Augmented Generation)给 LLM 外接一个可检索的知识库:
生成答案**之前**,先按问题从库里找出相关片段,拼进 prompt 作为参考,
让模型"开卷考试"而不是"闭卷默写"。

本篇按"为什么 → 流程 → 每个部件的原理 → 怎么评估 → 怎么坏、怎么修"展开。

## 1. 为什么需要 RAG:三条知识注入路线

LLM 的知识有三个天然短板:训练完成后**知识冻结**(不知道新信息)、
**不懂私有数据**(内部文档、个人笔记不在训练集里)、
**会幻觉**(不知道的内容也会一本正经地编)。

给模型补充知识,工程上主要三条路线:

| 路线 | 机制 | 更新成本 | 可溯源 | 适用场景 |
|---|---|---|---|---|
| 微调/继续训练 | 知识写进**参数** | 高(要训练) | 否 | 领域风格、稳定知识 |
| 长上下文直塞 | 知识放**输入**,全文给出 | 低 | 是 | 库小、问题需通览全文 |
| **RAG** | 知识放**输入**,按需检索 | 低(改库即可) | 是 | 库大、问题只涉及局部 |

RAG 的核心优势:知识库与模型解耦——改知识不用动模型,
答案还能附上出处(引用),方便核验、抑制幻觉。

## 2. 整体流程

**离线建库(Indexing,一次性的):**

```
文档 → 清洗/解析 → 切分成 chunk → embedding 模型编码成向量 → 写入向量数据库(建索引)
```

**在线问答(Retrieval + Generation,每次提问):**

```
问题 → (可选:改写/扩展) → 检索 top-k chunk → (可选:rerank 精排)
     → 拼进 prompt("根据以下资料回答:...") → LLM 生成 → (附引用)
```

两段共用的关键假设:**语义相近的文本,其向量也相近**。
检索于是变成向量空间里的最近邻问题——这是全篇的枢纽。

## 3. Embedding:把文本映射到向量空间

### 3.1 双塔模型与对比学习

embedding 模型通常是独立的中小模型(BERT 系或 LLM 改造的 encoder),
把变长文本压成一个 $D$ 维向量(常见 512~4096 维)。
训练方式是**对比学习**:构造"问题-正例文档-负例文档"三元组,
用 InfoNCE 损失拉近正例、推开负例:

$$\mathcal{L} = -\log \frac{\exp\!\big(s(q, d^{+})/\tau\big)}
{\exp\!\big(s(q, d^{+})/\tau\big) + \sum_j \exp\!\big(s(q, d_j^{-})/\tau\big)}$$

其中 $s(q, d)$ 是 query 与文档向量的相似度, $\tau$ 是温度。
负例的质量(尤其"难负例")很大程度上决定模型的区分能力。

### 3.2 相似度度量

向量一般先做 L2 归一化,此后点积 = 余弦相似度:

$$\cos\theta = \frac{q \cdot d}{\|q\|\,\|d\|}, \qquad
\|q\| = \|d\| = 1 \;\Rightarrow\; \cos\theta = q \cdot d$$

归一化带来的工程红利:检索就是矩阵乘法,硬件友好;
相似度落在 $[-1, 1]$,分数可跨库比较。

### 3.3 能力边界

稠密向量擅长**语义泛化**("汽车"能召回"轿车"),
但对**精确符号**天然弱:编号、型号、代码标识符、生僻专有名词,
在向量空间里常常被"抹平"到近义区域。这正是 §5 稀疏检索存在的理由。

## 4. 向量索引:ANN 近似最近邻

库有 $N$ 个 chunk,暴力检索的代价是 $O(ND)$ 次乘加
—— $N$ 到百万级以上就扛不住在线延迟。工程上用**近似最近邻(ANN)**索引,
拿一点点召回率换数量级的加速:

| 索引 | 思想 | 调参旋钮 | 特点 |
|---|---|---|---|
| IVF | 先聚类,只在最近的若干个簇内搜 | `nprobe`(查几个簇) | 简单、内存省,常与量化组合 |
| HNSW | 分层小世界图,从稀疏层逐层贪心走近 | `ef_search`(搜索宽度) | 召回/延迟比最好,内存开销大 |
| PQ | 把向量分段量化成码字,距离用码表近似 | 码本大小 | 内存压缩 10~100 倍,精度有损 |

共性权衡:**召回率 vs 延迟 vs 内存**,三者只能取其二地好。
实践中 HNSW 是默认选项;库极大或内存紧张时 IVF+PQ(如 FAISS 的组合索引)。
实现原理深挖(维度灾难、HNSW 手算)见 [02-vector-index.md](02-vector-index.md)。

## 5. 稀疏检索:BM25 与混合检索

### 5.1 BM25

经典统计检索模型,把文档看成词项集合,按词频与逆文档频率打分:

$$\mathrm{BM25}(q, d) = \sum_{t \in q} \mathrm{IDF}(t) \cdot
\frac{f(t, d)\,(k_1 + 1)}
{f(t, d) + k_1\Big(1 - b + b\,\dfrac{|d|}{\mathrm{avgdl}}\Big)}$$

- $f(t, d)$:词项在文档中的频次,饱和参数 $k_1$ 控制"词多出现几次后加分见顶";
- $|d| / \mathrm{avgdl}$:文档长度归一, $b$ 控制惩罚力度;
- $\mathrm{IDF}(t)$:越稀有的词越值钱。

底层是倒排索引,毫秒级、可解释、对精确词匹配极强。

### 5.2 混合检索

稠密与稀疏的失败模式几乎正交:一个懂语义但糊精确符号,
一个认死词但不懂同义。工程上的标准做法是**两路并行召回再融合**,
最常用 RRF(Reciprocal Rank Fusion)——不看分数只看名次,规避两路分数不可比:

$$\mathrm{RRF}(d) = \sum_{r \in \text{rankings}} \frac{1}{k + r(d)}$$

$k$ 常取 60。任一榜单里名次靠前的文档都能获得稳定加分。

## 6. Rerank:召回求快,精排求准

为什么检索和排序要分两阶段?看两种结构的代价:

- **bi-encoder**(检索用):query 和文档**各自**编码,向量可离线预计算,
  在线只是点积——快,但两塔在编码前没有交互,精度受限;
- **cross-encoder**(精排用):query 与文档**拼接**后一起过模型,
  逐 token 交互,判相关性准得多——但每对(query, doc)都要跑一次,
  $O(k)$ 次前向,只能用于小 $k$。

于是形成漏斗:召回阶段(稠密+稀疏)取 top-50~100,
cross-encoder 精排后只留 top-3~10 给 LLM。

## 7. Chunking:粒度就是信噪比

切块的粒度直接决定检索质量,是 RAG 里最值得调的自由度:

- chunk **太大**:一段里混多个主题,向量是"平均语义",检索噪声大;
  且塞进 prompt 浪费上下文预算;
- chunk **太小**:切断语义(半句话、脱离上文的代词),
  embedding 看不出它属于哪个主题。

常见策略:

| 策略 | 做法 | 备注 |
|---|---|---|
| 定长滑窗 | 固定 token 数 + 重叠 10~20% | 兜底方案,重叠缓解切断 |
| 结构切分 | 按标题/段落/代码块边界 | 文档规整时首选 |
| 父子块 | **小块做检索**,命中后把**大块(父)给 LLM** | 检索精度与上下文完整性兼得 |
| 语义切分 | 按 embedding 相似度找话题断点 | 成本高,收益不稳定 |

另外两条低成本高收益的经验:chunk 带上**元数据**(来源、标题路径、日期),
检索时可过滤、生成时可引用;以及给每块**前缀补上所属标题**,
缓解"脱离上下文"问题。

## 8. 生成侧:把检索结果变成答案

- **prompt 拼装**:典型模板是"指令 + 检索片段(编号、注明来源) + 问题",
  并要求模型**基于资料回答、答不了就说不知道**——显式授权拒答,
  是抑制"检索没命中还硬编"的关键;
- **引用**:让模型在句子后标注片段编号,用户可回溯核验;
- **知识冲突**:检索内容与模型参数记忆矛盾时,需在指令里明确优先级
  (一般以检索资料为准,尤其是时效性内容);
- **预算分配**:top-k $\times$ chunk 长度受上下文窗口约束,
  塞入过多片段反而会稀释注意力(见 §11)。

## 9. 评估:检索与生成分开算账

RAG 是两段系统,瓶颈定位必须分开评估。

**检索侧**(有标注的相关文档集合时):

| 指标 | 含义 |
|---|---|
| Recall@k | 相关文档有多少进了 top-k(召回够不够) |
| MRR | 第一个相关文档名次的倒数(排得靠前吗) |
| nDCG | 考虑名次加权的整体排序质量 |

**生成侧**(常用 LLM-as-judge 或专用框架如 RAGAS):

- **Faithfulness(忠实度)**:答案是否被检索片段支持——直接度量幻觉;
- **Answer Relevance**:答案是否回应了问题;
- **Context Precision/Recall**:塞给模型的片段里有用信息占比。

经验法则:答案不好时先看检索侧 recall——**检索没召回,生成再好也没用**。

## 10. 常见失败模式与进阶变体

| 失败模式 | 原因 | 对策 |
|---|---|---|
| 召回缺失 | embedding 不懂该问法 | query 改写、HyDE、混合检索 |
| 多跳问题答不出 | 答案分散在多个文档,单次检索覆盖不了 | 问题分解、迭代检索 |
| 片段答非所问 | 检索相关但不含答案 | rerank、父子块 |
| 全局性问题失败 | "整库主要在讲什么"无法靠局部片段回答 | GraphRAG / 预摘要 |

几个值得知道的变体:

- **HyDE**:先让 LLM 编一段"假想答案",用它的向量去检索
  ——答案与答案在向量空间里比问题与答案更近;
- **Query 改写/分解**:多轮对话里的指代消解("它怎么样"→补全实体),
  多跳问题拆成子问题分别检索再汇总;
- **Agentic RAG**:把检索封装成工具,由 agent 自主决定何时查、查几次、
  查什么——RAG 从"固定流水线"退化为 agent 的一个 tool,
  这是当前 agent 系统里知识获取的主流形态;
- **GraphRAG**:离线抽取实体-关系图谱并做社区摘要,
  用于回答跨文档的全局性问题。

## 11. RAG vs 长上下文:互补而非替代

长上下文模型(百万 token)普及后,"还要不要 RAG"是常见争论。定量地看:

- **成本**:全文塞入的 prefill 成本随库大小线性增长,且每次提问重复支付
  (prefix caching 只能缓解同前缀);RAG 只支付 top-k 片段;
- **注意力稀释**:上下文越长,关键信息被淹没的风险越高——
  "迷失中间"(lost in the middle)现象表明模型对长输入中段内容的利用显著下降;
- **各自的甜区**:库小/需通览全文(如整本小说分析)用长上下文;
  库大/问题局部化/需频繁更新用 RAG。

实践中的趋势是两者合体:长上下文把 RAG 的 top-k 上限放宽,
检索负责"从海里捞针",长上下文负责"把针周围的布料也一起给模型"。
