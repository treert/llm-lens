# grep 与文本扫描:为什么编码 agent 不需要向量检索

编码 agent(CodeBuddy、Claude Code、Aider 等)检索代码靠 grep 而非
embedding——这不是偷懒,而是检索理论与工程约束共同推导出的合理设计。
本篇回答:grep 凭什么够、它底下是什么算法、什么场景它会输,
以及它与 [08-advanced-rag.md](08-advanced-rag.md) 的 agentic 检索是什么关系。

## 1. 先看查询与语料的性质

检索方案的选择永远从"查什么、查谁"出发:

| | 代码检索 | 自然语言知识库 |
|---|---|---|
| 查询 | 精确符号为主(函数名、错误码、标识符) | 模糊语义为主("认证逻辑在哪") |
| 语料 | 标识符密集、有编译器级结构 | 自由文本、结构弱 |
| 变更频率 | 高(每分钟都在改) | 低(相对稳定) |
| 规模 | 万~百万行(MB~百 MB 级) | 百万~亿 chunk |

回忆 [01-rag.md](01-rag.md) §3.3:稠密向量的盲区恰是**精确符号**
(`get_model_dir` 与 `set_model_dir` 在向量空间里是近邻);
而 [03-bm25.md](03-bm25.md) §7 说稀疏检索的主场正是精确匹配。
代码查询几乎全是后者——**向量检索从一开始就不对症**。

## 2. grep 底下的算法

### 2.1 正则:线性时间的保证

正则表达式经 Thompson 构造转成 NFA,多状态并行模拟,
匹配时间是文本长度的**线性** $O(nm)$( $m$ 为模式大小),
且没有回溯爆炸(ReDoS)风险——ripgrep 用的 Rust regex 引擎走的就是这条路。

### 2.2 字面量加速:Boyer-Moore

查询里往往含字面量片段(如 `def main`),此时用 Boyer-Moore 类算法:
**从模式串末尾开始比较**,失配时按"坏字符表"一次跳过多个字符,
最好情况只需比较 $n/m$ 次——**亚线性**,看的字符比文本还短。
ripgrep 还会从正则中提取"内部字面量",先用 SIMD 指令做字面量预过滤,
候选行才进完整正则引擎。

### 2.3 带宽账:扫描为什么这么便宜

纯扫描的代价 = 把语料读一遍。对照硬件(参 [../inference/07-gpu-hardware.md](../inference/07-gpu-hardware.md)
的带宽概念):NVMe SSD 约 5 GB/s,内存约 50 GB/s,
而 mmap + 操作系统的 page cache 让**热数据常驻内存**——
一个 100 MB 的代码库,热查询是毫秒级。

结论:语料在百 MB 级时,**现查比维护索引便宜**。
索引的意义是摊销"反复查询"的成本,而代码库变更频率高,
索引的维护成本还摊不回来,语料又已经变了。

## 3. grep 的短板与 agent 的补法

grep 有两个本质短板,编码 agent 各自有解:

**只会布尔、不会排序**。grep 返回所有命中,没有相关性名次。
agent 的补法:人不看全量结果,agent 靠**迭代收窄**——
命中太多就加约束(限定目录、文件类型、更长的字面量),
这相当于把"排序"外包给了模型的判断。

**不懂语义、不懂结构**。"谁调用了这个函数"grep 只能近似。
agent 的补法:结构问题交给 **LSP**(定义/引用/类型是编译器级真值),
grep 只管文本面的粗筛——两个工具按问题类型分工。

## 4. agent 循环 = 用策略补偿检索器

编码 agent 的检索行为可以写成这样一个循环:

```
当前线索 = 用户问题里的符号/关键词
while 未定位到目标:
    hits = grep(当前线索)            # 弱检索器
    文件 = 按路径/类型/上下文挑选(hits)  # 模型当"人肉 reranker"
    读文件 → 提取新符号/新线索          # 查询扩展
```

对照 [08-advanced-rag.md](08-advanced-rag.md) §2:
这正是 agentic 检索——检索器极弱(布尔匹配),
但**策略极强**(模型决定查什么、什么时候停)。
传统 RAG 把智能放在检索器里(向量 + rerank,一次命中);
编码 agent 把智能放在策略里(grep,多步逼近)。
同一份预算,花在了不同的地方。

为什么代码场景"策略路线"赢?因为第 1 节的语料性质:
精确符号查询下,弱检索器的每一步反馈都是**确定性的**
(命中/未命中没有模糊地带),模型的下一步决策信息完整、迭代收敛快。
而语义查询里每次检索的结果都"似是而非",迭代反而容易漂移——
那是向量 + rerank 的主场。

## 5. 一张频谱:从无索引到端到端

把所有方案排在"索引投入"的轴上:

```
grep(零索引) → 倒排索引(BM25,03 篇) → 向量索引(ANN,02 篇) → 端到端长上下文
   现查现算      预建词项索引              预建语义索引            不检索,全塞
   ← 语料小/变更快/精确符号          语料大/稳定/模糊语义 →      语料很小
```

选择 checklist:

1. 查询是精确符号还是模糊语义?——前者向左,后者向右;
2. 语料多大、变多快?——小而快变向左,大而稳定向右;
3. 有没有 agent 循环?——有,检索器可以向左降一档,靠策略补。

编码 agent 的答案落在最左端,不是向量检索不好,
而是这道题的参数(精确符号 + 高频变更 + 百 MB 级 + 有 LSP 真值)
把最优解推到了"零索引 + 强策略"的角落。

## 6. 反向情况:代码场景什么时候也需要向量检索

第 1 节的参数一变,结论就翻转:

- **语料大到迭代 grep 收敛太慢**:百万行级 monorepo 里,
  每次全扫的延迟随 agent 步数线性叠加,预建索引开始划算;
- **查询本身是语义的**:不知道任何标识符的提问
  ("处理用户认证的逻辑在哪"),grep 无从下手,
  恰是稠密向量的主场([01-rag.md](01-rag.md) §3);
- **真实产品因此是混合路线**:Cursor 的 codebase indexing、
  Sourcegraph 等确实会建 embedding 索引——向量负责语义召回,
  grep/LSP 负责精确符号与结构真值,
  正是 [01-rag.md](01-rag.md) §5.2 混合检索在代码域的翻版。
